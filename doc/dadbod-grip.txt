1. INTRODUCTION                                          *grip-introduction*

dadbod-grip.nvim is a database client for Neovim with support for
PostgreSQL, MySQL, SQLite, DuckDB, MotherDuck, and read-only SQL Server.
Each engine gets schema browsing and metadata inspection; writable engines
also support inline cell editing.

Renders query results as editable grids with visual change staging,
sort/filter/pagination, foreign key navigation, schema browsing, and a
SQL query pad. Works standalone or alongside vim-dadbod-ui.

Quick start: >
  :GripConnect                  pick or add a database connection
  :GripSchema                   browse tables with columns and types
  :Grip users                   open a table in an editable grid
  :GripQuery                    open a SQL scratch pad
<

==============================================================================
2. REQUIREMENTS                                          *grip-requirements*

- Neovim 0.10 or later
- One or more database CLI tools in PATH:

  PostgreSQL ......... psql
  SQLite ............. sqlite3
  MySQL/MariaDB ...... mysql (both use compatible --batch output)
  DuckDB ............. duckdb
  SQL Server ......... sqlcmd (read-only grid support in v1)

3. INSTALLATION                                              *grip-install*

lazy.nvim (recommended): >lua
  {
    "joryeugene/dadbod-grip.nvim",
  }
<
The plugin ships a lazy.lua package spec, so you do not need to copy a
cmd = { ... } command list into your config. Leaving cmd out avoids stale
command lists when new :Grip* commands are added.

With keymaps: >lua
  {
    "joryeugene/dadbod-grip.nvim",
    keys = {
      { "<leader>lg", function() require("dadbod-grip").open_smart() end,
        desc = "Grip: Open grid" },
      { "<leader>gs", "<cmd>GripSchema<cr>", desc = "Grip: Schema browser" },
      { "<leader>gt", "<cmd>GripTables<cr>", desc = "Grip: Table picker" },
      { "<leader>gq", "<cmd>GripQuery<cr>", desc = "Grip: Query pad" },
      { "<leader>gc", "<cmd>GripConnect<cr>", desc = "Grip: Connect" },
    },
    opts = {},
  }
<
Local checkout for development/testing: >lua
  {
    "joryeugene/dadbod-grip.nvim",
    dir = "~/Documents/GitHub/dadbod-grip.nvim",
  }
<
Keeping the GitHub repo string as the first field preserves lazy.nvim's plugin
identity while loading files from your local checkout.

Grip's standalone SQL completion is built in. No additional plugins are
required; blink.cmp and nvim-cmp are optional alternative frontends.
To verify your setup after installation: >
  :checkhealth dadbod-grip
<
packer.nvim: >lua
  use {
    "joryeugene/dadbod-grip.nvim",
  }
<

4. CONFIGURATION                                              *grip-config*

setup() is called automatically by the plugin loader with sensible defaults.
Override if needed: >lua
  require("dadbod-grip").setup({
    limit            = 100,
    max_col_width    = 40,
    timeout          = 10000,
    engine_timing    = false,
    completion       = true,
    connections_path = nil,
    picker           = "builtin",
    pinned_max       = nil,
    cell_split       = "horizontal",
    sticky_header    = true,
    open_sidebar     = true,
    show_running_time = true,
    show_result_time  = true,
    show_hints        = true,
    highlights        = {},
  })
<
When `completion` is false, grip's built-in TextChangedI popup is disabled.
Use blink.cmp or nvim-cmp as the completion engine instead. See |grip-install|
for source configuration examples.

When `connections_path` is set, grip reads and writes connections to that single
file only (skips the project-local + global merge). Useful for a centralized
connections file shared across projects.

`timeout` applies to database CLI calls. DuckDB work that may download an
extension or read a remote URL gets a 60-second minimum for that network step.
Health pings use 5 seconds.

                                                        *grip-highlights*
Highlight overrides ~

`highlights` maps Grip group names to |nvim_set_hl()| style definitions.
For selection colors that follow a light or dark colorscheme: >lua
  require("dadbod-grip").setup({
    highlights = {
      GripColHighlight = { link = "Visual" },
      GripHeaderActive = { link = "Visual" },
      GripNull = { link = "Comment" },
    },
  })
<
Grip applies built-in definitions first, then the current connection accent,
then your overrides. An override REPLACES the entire group; unspecified
attributes do not inherit Grip's colors or styles. An empty definition (`{}`)
clears a group. Links follow the target group when the colorscheme changes.
Use `fg`/`bg` for explicit GUI colors and `ctermfg`/`ctermbg` for terminal colors.
The `default` and `force` control flags are not supported: configured overrides
always take precedence.

Overrides are reapplied when grids open, after `:colorscheme`, and on connection
switches, including reconnecting or leaving a colored connection. A later
`setup()` replaces the map; omitting `highlights` or passing `{}` restores
built-in definitions and the current connection accent. With no overrides,
Grip's existing appearance is unchanged.

Supported groups:
  GripHeader         GripHeaderActive   GripColHighlight   GripColType
  GripNull           GripNullStaged     GripReadonly       GripModified
  GripDeleted        GripInserted       GripStatusOk       GripStatusChg
  GripNegative       GripBoolTrue       GripBoolFalse      GripDatePast
  GripUrl            GripWatch          GripConnAccent     GripConnAccentBold
  GripBorder

Invalid maps, unknown group names, and invalid highlight definitions raise a
setup error before changing live options or visible groups. Define linked
target groups in your colorscheme, as you would for other Neovim highlights.

                                                        *grip-query-timer*
Operations wrapped in grip's loading float, such as opening a table or
generating SQL, show a centered indicator. Once the work passes half a
second the float starts counting up next to its label, so the wait is
visible before the grid appears: >
    querying users... 3.4s
    generating SQL... 1m12s
<
The reading is wall time for the whole operation, including nested steps.
Set `show_running_time = false` to hide its elapsed number while keeping the
animated loading indicator and operation label. It resets for the next
operation. Long labels shorten to keep the elapsed time visible. The counter
measures waiting; it does not report database progress or identify a hung query.
CLI timeouts apply separately to each call, so a multi-step operation may take
longer.
After a successful query, the results footer keeps its client-observed
round-trip, such as "Query: 3.4s client" or "Query: 17ms client". This duration
measures db.query, including the client process and result parsing. It excludes
column/primary-key lookups, pagination counts, and rendering, so it can be
shorter than the running whole-operation clock. History keeps the same query
duration in milliseconds. The footer stays visible during horizontal data
scrolling; narrow windows shorten its label. If the SELECT fails or is
interrupted, the previous result and its original duration stay in place.

                                                        *grip-engine-timing*
Set `engine_timing = true` to opt in to DuckDB profiler latency collection.
The result footer adds a separate "Engine: 12.3ms DuckDB profiler latency"
line. This is DuckDB's JSON-profile LATENCY for the statement that produced
the result, converted from seconds to milliseconds. It includes the adapter's
nested-value SELECT conversion. Attachment setup, CLI startup, and Lua result
parsing are outside this metric. It is elapsed query latency, not cumulative
operator CPU, network latency, or the execution time of a remote attached DB.
The existing client clock keeps its own meaning. Collection is independent
of timing display preferences and adds profiling overhead.
Actual database writes also opt in. After a successful reload, "Write engine"
retains the write's profiler latency separately from that SELECT's "Engine".
Metadata and later unrelated refreshes inherit neither write duration.
`show_result_time = false` hides Engine and Write engine with client timings;
collection continues. `show_hints` controls Zen shortcuts independently.
The first eligible call probes JSON/ALL support once using a synthetic SELECT
in a fresh in-memory client without an init file or attachments. Results are
cached per executable identity; its time belongs to that first client clock.
An unsupported client keeps the normal query path with absent engine timing.
Cancelling or timing out the probe aborts the request before user SQL starts.

Only eligible single statements are profiled. Batches, transaction wrappers,
session/profiling commands, and conservatively unsupported syntax keep the
normal conversion/compatibility path and report unsupported timing. A profile must
match the submitted adapter statement exactly (apart from outer whitespace).
Missing, malformed, or mismatched profiles report unavailable timing. Neither
absence becomes a numeric zero. An enabled profile never runs EXPLAIN ANALYZE
or retries its statement; its wrapper errors are returned without compatibility
fallback. When profiling is disabled, legacy conversion/fallback is preserved.
DuckDB JSON profiling with ALL coverage is required; this
collector is exercised against DuckDB 1.5.5.

Each profile is written inside a new private temporary directory (0700) and
removed after success, failure, timeout, interruption, or parsing failure.
No database privileges or settings are changed persistently. Timing does not
change transaction semantics or promise rollback after a failed batch.

The additive Lua facade also accepts per-call options: >lua
  local db = require("dadbod-grip.db")
  local result, err = db.query("SELECT 42", url, { engine_timing = true })
  local written, write_err = db.execute(sql, url, { engine_timing = true })
<
Successful results gain `engine_timing`: status is "available", "unsupported",
or "unavailable". Only "available" has `elapsed_ms`; DuckDB also identifies
`source = "duckdb_profile"` and `scope = "statement"`. Absent data has a
machine-readable `reason`. Calls without the option keep their existing
result shape. PostgreSQL, MySQL/MariaDB, SQL Server, and SQLite currently
return "unsupported"; their client durations remain available as before.
See doc/engine-timing.md for the support matrix and upstream metric contracts.
Mutation previews and confirmed database writes use the same loading clock.
This includes staged apply (also imported rows), local file write-back,
committed-transaction undo, and DDL. A write finishes its clock before its
separate SELECT reload begins. After that reload succeeds, the status line
keeps "Write: 1.4s client" alongside the SELECT's own Query duration. Write
measures the db.execute call, including client startup and lock waits; it is
not server execution time. That Write duration belongs to those refreshed
rows: metadata and later unrelated SELECT results do not inherit it.
Successful apply history also keeps the write duration in milliseconds.

Import parsing/staging and AI generation are not database writes. The loading
clock updates while client waits pump Neovim's event loop; CPU-only local
preview staging can pause animation. An interrupted client wait closes the
indicator but does not prove the server stopped or rolled back the write.
Grip reports the database outcome as unknown for interrupted/timed-out client
waits. Refresh and check the database before retrying. If you navigate or edit
while a write waits, its completion keeps your newer view and staging intact.

Set `show_result_time = false` to hide retained Query, Write, and action
durations in the result grid. Completed action status, errors, row counts, and pagination
remain visible. This option and `show_running_time` are independent and both
default to true. They control display only: queries and actions are still
timed, and history keeps its durations. Neither setting changes key hints,
the sticky header, or whether the sidebar opens.

Set `open_sidebar = false` to connect directly into the main workspace. The
sidebar remains available through :GripSchema, `gb`, or `1`.

Set `show_hints = false` for Zen display: hide automatic shortcut/decorative
help in the grid, SQL pad, sidebar, and welcome screen. Essential result status,
column labels, data/NULLs, staged colors/counts, read-only and hidden-column
markers, filters, pagination/totals, loading, and errors remain available.
Narrow grids may use extra status rows so fields remain readable. Explicit `?`
help (or its configured binding) still works. New SQL-pad help uses decorations;
changing modes never rewrites existing SQL or comments. `:GripZen` toggles this
setting for the current session without changing either timing option, keymaps,
pane geometry, or zoom. No default key is added. A cursor on a removed help row
may naturally clamp to the last remaining line.

                                                             *grip-picker*
When `picker` is set to "telescope" or "snacks", simple pickers (table picker,
command palette, history) delegate to that backend. Complex pickers
(connections, saved queries) always use the built-in picker. Falls back to
built-in gracefully when the configured backend is not installed.

                                                          *grip-pinned-max*
`pinned_max` caps how many results can be pinned at once. Add it to your
existing `setup()` call: >lua
  require("dadbod-grip").setup({
    pinned_max = 2,
  })
<
When the cap is reached, `gL` refuses to pin and notifies you to unpin
something first. Unset (nil, the default) means no cap.

                                                          *grip-cell-split*
`cell_split` controls how the full-buffer cell editor (`gB`) opens:
"horizontal" (default) splits below the grid at ~40% height, "vertical"
splits at ~40% width. See |grip-cell-buffer|.

                                                       *grip-sticky-header*
`sticky_header` (default true) mirrors the grid's column-name row into the
window's 'winbar', so the column names stay visible once a table taller than
the window scrolls past them. The column under the cursor is highlighted
there with the same background the grid uses for it, and the mirrored row is
sliced to follow horizontal scrolling, so it stays aligned with the cells
underneath on wide tables. The watch/write badges keep the right edge of the
winbar and the header yields that space to them.

While the grid's own header row is still on screen there is nothing to repeat,
so the winbar goes blank instead of showing the column names twice. Blank, not
absent: an unset 'winbar' hands the line back to the window, which would shift
the whole grid by one row every time scrolling crosses that threshold.

A winbar costs one screen line per grid window; set `sticky_header = false`
to reclaim it for good (the badges then render as before).

The shortcut hints below the result fit into two rows for each window's text
width. They use configured keys and stay in place during horizontal table
scrolling. Narrow windows prioritize core actions and help; `…` marks omitted
hints when it fits. These rows scroll vertically with the end of the result.

AI SQL generation (optional): >lua
  require("dadbod-grip").setup({
    ai = {
      provider = nil,       -- nil = auto-detect, or "anthropic"/"openai"/"gemini"/"ollama"
      model = nil,          -- nil = provider default
      api_key = nil,        -- nil = env var, "env:VAR", "cmd:op read ...", or direct string
      base_url = nil,       -- override for ollama or proxy
    }
  })
<
Provider auto-detection priority: ANTHROPIC_API_KEY > OPENAI_API_KEY >
GEMINI_API_KEY > ollama (local). Explicit provider setting always wins.

To disable AI entirely (skips schema pre-warm, info message on A/gA): >lua
  require("dadbod-grip").setup({ ai = false })
<

==============================================================================
5. COMMANDS                                                 *grip-commands*

All commands are global and available after the plugin loads.

                                                                     *:Grip*
:Grip [table|SQL|file|URL]
  Open a table in an editable grid, run a SQL query, open a local file,
  or query a remote file via DuckDB httpfs.

  Examples: >
    :Grip users
    :Grip SELECT * FROM orders LIMIT 50
    :Grip /path/to/data.parquet
    :Grip https://example.com/data.csv
<

                                                               *:GripSchema*
:GripSchema
  Open or focus the schema browser sidebar. Shows tables and views with
  expandable columns, type abbreviations, and PK/FK markers. The `gb`
  keymap focuses the sidebar from the grid or query pad, or closes it when
  already inside the sidebar.

                                                               *:GripTables*
:GripTables
  Open the table picker. Shows a floating list with column preview (PK,
  FK markers, and types). Uses grip_picker with zero external dependencies.
  Also reachable via `gT` or `gt` from every primary surface. `go` is the
  short picker key in the grid and query pad; in the sidebar it opens the
  table under the cursor with newest rows first.

                                                                *:GripQuery*
:GripQuery [sql]
  Open a SQL query pad. Optionally pre-fill with a SQL string. In normal or
  insert mode, press <C-CR> to execute the blank-line-delimited SQL block
  under the cursor into a grip grid.

                                                                 *:GripSave*
:GripSave [name]
  Save the current query pad content to .grip/queries/{name}.sql.
  Prompts for a name if not provided.

                                                                 *:GripLoad*
:GripLoad [name]
  Load a saved query into the query pad. Shows a picker if no name is
  provided.

                                                              *:GripConnect*
:GripConnect [url]
  Switch database connection. Shows a picker if no argument is provided.
  Reads from .grip/connections.json, g:dbs (DBUI compatible), and
  $DATABASE_URL.

                                                              *:GripExplain*
:GripExplain [sql]
  Query Doctor: translates EXPLAIN plans into plain-English health
  checks. Shows severity (SLOW/WARN/OK), proportional cost bars,
  and actionable suggestions (e.g. "add an index on the filtered
  column"). Works across PostgreSQL, MySQL, DuckDB, SQLite, and
  SQL Server.

                                                          *:GripProperties*
:GripProperties [table]
  Show full table properties in a floating window. Includes columns with
  types, primary keys, foreign keys, indexes, row estimate, and table size.
  Uses the current grip table if no argument is provided.

                                                              *:GripProfile*
:GripProfile [table]
  Open a data profiling report showing per-column statistics with Unicode
  sparkline distributions. Shows completeness, cardinality, min/max, and
  top values. Adapts to narrow terminals with a stacked layout.

                                                                 *:GripAsk*
:GripAsk [question]
  Generate SQL from a natural language question using AI. Schema context
  is auto-assembled from database metadata. Result appears in the query
  pad for review before execution.

  Providers: Anthropic, OpenAI, Gemini, Ollama (local).
  Auto-detects from env vars: ANTHROPIC_API_KEY > OPENAI_API_KEY >
  GEMINI_API_KEY > ollama fallback. Override with setup({ai={...}}).

7. EDITING                                          *grip-editing-workflow*

Grip uses a staging model for edits. Changes are staged in memory and
color-coded in the grid before being applied to the database.

Color coding:
  Violet ........... Modified cell (staged change)
  Red .............. Row marked for deletion
  Green ............ Newly inserted row

Workflow:
  1. Edit cells with `i` or `<CR>`, set NULL with `x`, paste with `p`
  2. Insert rows with `o`, mark deletions with `d`
  3. Preview staged SQL with `gs` or live preview with `gl`
  4. Apply all changes with `a` (wraps in BEGIN/COMMIT transaction)
  5. Undo individual edits with `u` or reset all with `U`

Structured grid writes run in one transaction. A guard or statement failure
rolls back that batch and preserves staged changes. A timed-out or interrupted
client can leave the outcome unknown; inspect and refresh before retrying.

Multi-level undo: every edit operation pushes the previous state onto a
50-deep undo stack. Press `u` repeatedly to step back through your edit
history. Press `U` to reset to the original state in one step.

Committed Undo ~

After applying staged edits, `u` performs a guarded compensating row operation.
It uses identities captured in that write's session, including post-edit keys,
and requires the stored current values to match. A conflict or missing row
rolls back the reversal and retains the Undo entry. This is not a universal
transaction rollback: triggers may run again, and arbitrary trigger effects on
other rows or tables are not reversed. If exact target-row restoration cannot
be proved, Undo fails without consuming its entry.

Generated identities are supported through SQLite rowid, PostgreSQL RETURNING,
DuckDB RETURNING, MariaDB INSERT RETURNING, and MySQL's single auto-increment
primary key. MySQL/MariaDB grid writes require InnoDB and enforced CHECK
constraints. ENUM/SET definitions must have unique nonempty ASCII labels made
of letters, digits, underscores or hyphens. Empty, case-equivalent, escaped or
otherwise unproven labels refuse the entire batch before writing. Spatial row
restoration is also unsupported. Custom SQL remains available.
SQLite generated keys in WITHOUT ROWID tables, tables shadowing
all rowid aliases, and MySQL incomplete non-auto-increment or composite keys
require explicit complete keys. A batch containing an unsupported generated
identity is refused before any row changes; no partial Undo is offered. NULL,
missing, or unproven row keys also fail closed. SQL Server grids remain read-only.
Failed writes after submission remain uncertain unless rollback is proved.
They are never retried automatically. If original client completion is still
unknown, refresh refuses to discard staging or clear the write guard. After
confirmed client exit, inspect and refresh before taking a new action. An
uncertain Undo entry cannot be replayed.

Lossless SQLite reads require UTF-8 database encoding and SQLite 3.35 or newer
for MATERIALIZED result snapshots. UTF-16 databases are refused before the
original read; their encoding is never changed. Custom SQL execution remains
available, but unsupported result reads do not become editable grids.

MySQL/MariaDB typed reads evaluate the original SELECT once inside a derived
table. A LIMIT fence preserves materialization and original ORDER/LIMIT and
DISTINCT behavior. Known direct fields and explicit AS labels retain their
spelling, including quoted names. Source metadata before the read plans headers
only. The original read runs first in its transaction; source types, visibility
and the complete schema are checked afterward on that same client. Source
restoration is admitted only after matching receipts, COMMIT and client exit.
No TEMP table privilege is required, and read-only profiles keep server-side
transaction enforcement.

Column metadata can hide columns the account cannot see. Grip also compares
the complete quoted column names/order from SHOW CREATE TABLE with the type
metadata while the original read's metadata lock remains held. Invisible and
generated SQL columns are included. The bounded layout check requires
sql_quote_show_create enabled and the adapter's fixed SQL mode. On MySQL with
generated invisible-key support, show_gipk_in_create_table_and_information_schema
must be ON. An absent setting is accepted only on identified MariaDB or the
documented pre-GIPK MySQL 8.0.0--8.0.29 profile. Grip reads these settings and
does not change them or grant access. Native verification covers MySQL 8.4 and
MariaDB 11.8; this does not claim native testing on older server versions.

A successful pre-read check that establishes an unsupported visibility/layout
profile can select native read-only results before any original query runs.
Denied metadata, unknown visibility or ambiguous layout parsing is an error;
it cannot trigger a second route. A post-read layout mismatch withholds the
result after the one query ran. SHOW CREATE supplies only a SQL-column span
witness; type/charset metadata supplies physical types. Engine-internal hidden
storage is outside this layout contract.

Other safe single SELECTs, CTEs and set operations keep the original native
query and headers through a route chosen before execution. Session-context
reads also remain unwrapped. These results have unproven physical types and
remain read-only; this route makes no universal byte or NULL fidelity claim.
Explicit duplicate labels, batches on the SELECT route, INTO/locking clauses
and ambiguous client commands are refused before execution. Intentional custom
DDL/DML/routine batches remain a separate invocation path and are denied on
read-only profiles. Safe SHOW/DESCRIBE/EXPLAIN reads remain available.

Schema changes, unsupported types or unsafe warnings can withhold a result
after the query ran. A successful original is committed when a completed
metadata comparison or codec check withholds only its result. Actual metadata/client errors
close the session; commit or completion failures report uncertainty. No error,
denial or cancellation causes a fallback or automatic SQL replay.

Result provenance ~

A byte-encoding receipt is separate from proof of a column's physical SQL type
and editable source. Results with unproven source restoration remain read-only;
staging an apparent text value cannot upgrade that proof. Empty results and
all-NULL columns also require column-level proof. Metadata-only source records
and binding flags alone never establish an editable source.

Unproven bytes display as hexadecimal in the grid and the gB split inspector.
Text/JSON inspectors, clipboard yanks and exports refuse values whose encoding
is unproven. Encoding-proven text may be exported for presentation, but SQL
export, cloning and grid writes additionally require source restoration proof.
Page, all-row and batched file exports retain the original provenance. A
refused file export preserves any existing destination.

Empty text and SQL NULL ~

Empty text displays as `""`; SQL NULL displays as the NULL marker. Clearing an
ordinary value and saving stages empty text. Saving an untouched NULL buffer
stages nothing. The existing grid `x` action stages SQL NULL.

Inside either editable cell buffer, `:GripCellEmpty` stages empty text even
when the original value is NULL, and `:GripCellNull` stages SQL NULL. These
commands close the float editor; the split editor stays open. They only stage
a value. The grid's normal Apply confirmation still controls the database write.
An editor whose grid was refreshed, replaced, or navigated elsewhere refuses
stale saves and commands. Raw JSON text remains unchanged by no-op saves.

CSV and TSV exports encode NULL as an unquoted empty field and empty text as
`""`. JSON exports keep non-NULL cell text as strings, including numeric and
boolean spellings, instead of guessing a value's type from its characters.

Read-only mode is auto-detected when no primary key exists on the table or
the result omits any primary-key column, including part of a composite key
(grip needs the complete PK for WHERE clauses in UPDATE/DELETE statements).
Empty raw queries also stay read-only when the client returns no column metadata;
schema fallback still allows insertion into an empty full-table view. SELECT
projections with column aliases, including unchanged names such as `id AS id`,
or expressions such as `total * 2` and bare `CURRENT_TIMESTAMP` open read-only.
Supported direct column references and wildcards remain eligible for editing
when the normal primary-key requirements are met. This includes unquoted
Unicode column names and quoted or qualified columns named CURRENT_TIMESTAMP.
MySQL/MariaDB support backtick and double-quoted identifiers because the
adapter enables ANSI_QUOTES; executable comments in projections stay read-only.
PostgreSQL nested comments are skipped when checking columns and locating the
source table. Qualified columns and wildcards must match that table or its
alias. Struct projections such as DuckDB's details.* and details.status stay
read-only because their output names do not identify base-table columns.

Full-buffer cell editor ~
                                                        *grip-cell-buffer*
Press `gB` on a cell to open its value in a real split buffer (named
grip://cell/<table>/<row>/<column>) instead of the small float editor.
Built for large values: big JSON documents, long text.

  - JSON values open exactly as stored with ft=json (syntax highlighting
    and folding work as usual). Editing preserves large numbers, decimal
    spelling, key order, and whitespace outside your changes.
  - Prose columns (body, description, notes, content, text, bio) open
    with ft=markdown; everything else stays plain.
  - Multiline values round-trip exactly: the grid displays newlines as a
    return symbol, the buffer edits the real thing.
  - :w stages the buffer content as a change to that cell (nothing
    touches the database until `a`). Saving without textual changes
    stages nothing ("No changes").
  - NULL cells open empty. Save non-empty text to stage it; to keep the
    cell NULL just close without saving (:q).
  - On read-only grids the buffer opens in view mode and `q` closes it.

Split direction and size are configurable, see |grip-cell-split|.

JSON tree drilldown ~
                                                          *grip-json-tree*
Press `gK` on a JSON/JSONB cell to explore it as a collapsible tree
instead of squinting at a one-line blob: >

  ▾ $: {...} (2 keys)
      key: "value"
    ▾ nested: {...} (1 key)
        deep: true
<
Inside the float:

  <CR> / za       Toggle expand/collapse on the node under cursor
  j / k           Move between nodes
  y               Yank the value under cursor (containers yank
                  compact JSON; strings yank the raw string)
  gy              Yank the JSONPath of the node under cursor,
                  e.g. $.items[2].price or $["weird key"]
  q / <Esc>       Close

Objects render as {...} (N keys), arrays as [...] (N items), and keys
are sorted for stable output. null renders dimmed, booleans green/red.
The float opens with the top level expanded and children collapsed;
documents with 20 or fewer leaves open fully expanded.

`gK` also works inside the `K` row view: press it on any line to drill
into that column's JSON value. Non-JSON cells notify "Not a JSON cell".

Press `gn` to filter by IS NULL on the column under the cursor.
Press `gF` to open the filter builder: choose an operator (=, !=, >,
<, LIKE, IN, IS NULL, IS NOT NULL) and enter a value. Numeric strings
are passed unquoted; all others are single-quoted with escaping.
Press `<C-f>` to enter a freeform WHERE clause. Multiple filters are
AND-ed together. Press `F` to clear all filters.

An FK jump (`gf`, `gm`) scopes the grid with a WHERE clause of its own.
That clause is pinned: it is what the grid IS, not something you filtered,
so `F` and `X` leave it alone, the `[filtered]` badge ignores it, and `gP`
never bakes it into a preset. Use `<C-o>` to leave an FK context.

Filter presets ~
Press `gP` to save the current active filters as a named preset for the
current table. Presets are stored in `.grip/filters.json` keyed by table
name. Press `gp` to load a saved preset using the grip_picker float.

Paginate ~
Results are paginated (default 100 rows per page). The status line shows
the current page and total. Press `H`/`L` to navigate pages (or `]p`/`[p`),
or `]P`/`[P` to jump to the last/first page.

Press `X` to reset all sort, filter, and pagination state at once.

9. FOREIGN KEY NAVIGATION                               *grip-fk-nav-full*

Press `gf` on a cell that contains a foreign key value to navigate to the
referenced row in the target table. A new grid opens showing just that
row. Press `<C-o>` to go back. The title bar shows a breadcrumb trail
of your navigation path.

Press `gm` on any row to navigate the other direction: it opens the rows
in other tables that reference the current row (reverse foreign key).
If the cursor is on a column that other tables reference (usually the
primary key) its value is used; otherwise the row's primary key is used.
When exactly one table references the current one, the child grid opens
directly, filtered to `WHERE fk_col = <value>` (e.g. `orders.user_id ←
users`); when several do, a picker lists each `child_table.fk_column`.
The opened grid is fully functional, so reverse hops chain: users →
orders → order_items. Press `<C-o>` to walk back. Composite foreign
keys and NULL values are reported and skipped.

FK metadata is fetched automatically via information_schema (PostgreSQL,
MySQL, DuckDB), PRAGMA foreign_key_list (SQLite) or sys.foreign_keys
(SQL Server). Reverse lookups use a single query per table and are
cached per session; adapters without a native reverse query fall back
to scanning each table's foreign keys once.

10. SCHEMA BROWSER                                          *grip-schema*

Toggle with `:GripSchema` or `gb` from a grid or query-pad buffer. Opens a
left sidebar showing tables, views, functions, and procedures for the current
connection. When the adapter supplies schema metadata, schemas start collapsed.
Objects without schema metadata keep their flat sections, even when other
objects have known schemas. Missing metadata does not assign an object to
public or main. PostgreSQL objects always belong to a schema; an unqualified
display name does not mean the object has no schema.

PostgreSQL declarative partitions appear once beneath their actual parent in a
separate Partitions group. Nested partitions retain their hierarchy, and
cross-schema children show their schema. Children whose parent is not visible
remain at the top level. Traditional inheritance stays flat. Group counts show
visible direct children; browsing and expanding columns do not count data rows.
Opening a parent table uses the normal parent query, including its partitions.
Metadata visibility does not guarantee permission to query every column.

Schema browser keymaps:
  <CR>            Open table/routine, or toggle schema/partition group
  <S-CR>          Open table in new split
  l / zo          Expand group or table columns
  h / zc          Collapse item, or move to its parent
  L               Expand every schema/partition level; keep existing columns
  H               Collapse all groups and table columns
  /               Search hidden names and routine identity signatures
  n / N           Jump to next / previous visible table or routine
  F               Clear filter and restore the original folds and view
  r               Refresh schema (re-fetch table list)
  y               Yank table or column name to clipboard
  go              Open table under cursor, ORDER BY latest (created_at / PK DESC)
  gT / gt         Table picker (fuzzy finder)
  q               Focus query pad (pre-fills if empty; appends if pad has content)
  gq              Load saved query (picker with SQL preview)
  gw              Jump to grid window
  gC / gc         Switch database connection
  gh              Query history browser
  gb              Close sidebar (from inside; gb elsewhere: focus/open)
  D               Drop table (with typed confirmation)
  +               Create new table (interactive designer)
  <Esc>           Close sidebar
  ?               Toggle help popup

Search temporarily reveals matching paths without changing the saved folds.
Editing a filter keeps the original pre-search view; cancelling leaves the

Labels remain complete in the buffer. Use `zh`/`zl` to scroll horizontally,

The window edge indicates clipped text. Columns load on explicit table

13. CONNECTIONS                                          *grip-connections*

`:GripConnect` manages database connections from multiple sources:

  .grip/connections.json     project-local profiles (new connections save here)
  ~/.grip/connections.json   global profiles (shared across all projects)
  g:dbs                      vim-dadbod-ui compatible table (auto-saves to global)
  $DATABASE_URL              environment variable
  g:db / b:db                vim-dadbod variables

Add a new connection: >
  :GripConnect postgresql://user:pass@localhost/mydb
<
Or run `:GripConnect` with no arguments to pick from known connections
or add a new one interactively.

Connections are deduplicated by URL across all sources. The order is:

  1. discovered Docker containers
  2. .grip/connections.json          (project)
  3. ~/.grip/connections.json        (global)
  4. g:dbs
  5. $DATABASE_URL
  6. g:db / b:db

The first hit for a URL wins. Because the files are read before `g:dbs`, an
entry may keep its URL in `g:dbs` while its `color` and `mode` live in
connections.json.

One case merges rather than discards: a discovered container colliding with
a connections.json entry keeps the container's name and adopts the file
entry's `type`, `env_file`, `mode`, `color` and `attachments`. Discovery
contributes liveness, the file contributes configuration -- without this, a
connection saved as `"mode": "ro"` would connect writable whenever its
Docker stack happened to be up.

Connection scope ~

New connections added via the picker save to the project-local file
(.grip/connections.json). To make a connection available in every project,
press `G` on it in the picker to copy it to ~/.grip/connections.json.

Both files are merged when the picker opens. When at least one global
connection exists, connections are grouped under "global" and "project"
section headers so the scope is immediately visible without any extra
knowledge of the file layout.

Selecting a saved global connection updates its recency in the global file
without creating a project-local copy. Its settings and attachments continue
to come from that profile. If the same URL has a project-local profile, that
override keeps precedence and only its recency is updated.
Attachment changes also save to the profile's owning registry.

Press `D` in the connection picker to remove the selected saved profile from
its original registry after confirmation. Other profiles with the same name
are preserved. Deleting a local override reveals the global profile for that
URL on the next refresh. If the selected profile changed or is ambiguous,
reopen the picker before deleting. Unsaved and discovered-only rows have no
saved profile to remove; deleting a discovered row with saved settings removes
only those settings, and the live container can still appear. Built-in and
demo rows retain their separate dismissal behavior.
Removing a profile preserves every other stored record, including custom
fields. Malformed registry JSON is refused without changing the file.
Deletion requires a nonempty string `id`, or no `id` for a legacy profile;
numeric and other unsupported IDs are refused without changing the file.

`g:dbs` entries auto-persist to the global file so they appear in every
project without any extra steps.

To use a single shared file across all projects instead of the two-tier
system, set `connections_path` in your setup() call. See |grip-config|.

Local file discovery ~

When the connection picker opens it scans the current working directory for
supported data files and shows them in a "Local Files (cwd)" section.

Supported extensions: .parquet .csv .tsv .json .ndjson .jsonl .xlsx .orc .arrow .ipc

Selecting a file opens it connect-once (no save). Press `s` in the picker to
save the file as a named connection in .grip/connections.json.

Connection health ~

Each saved connection shows a session-scoped status indicator:

  *   connected this session (set automatically on successful switch)
      unknown (no indicator shown; not yet connected this session)
  x   failed (last attempt did not succeed)
  ?   unresolved (the entry's ${VAR} could not be expanded; see below)

Press `T` on any file-based connection in the picker to retest it instantly.
The indicator updates in place. Health state is session-only and never persisted.

Entry fields ~

Beyond `name` and `url`, an entry in either connections.json may carry:

  id         opaque saved-query binding, assigned lazily and kept on rename
  type       explicit adapter/file type when URL inference is insufficient
  env_file   path to a .env file supplying ${VAR} values for the url
  mode       "ro" to connect read-only, "rw" (or absent) to connect writable
  color      accent colour for this connection: a palette name
             (green, orange, red, blue, violet, yellow) or "#rrggbb"
  attachments DuckDB federation entries restored on reconnect

All are optional. Existing files remain readable and IDs are added lazily.

These fields exist only in a connections.json entry. `g:dbs` is read as the
vim-dadbod-ui format -- name and url and nothing else -- so a `color`,
`mode`, `env_file` or `type` written there is discarded on read.

Saved-query connection binding ~

New saved queries carry `-- grip:connection=<id>`, never a database URL or
password. Loading resolves that opaque ID across project, global, or custom
connection sources. Renaming, promoting, deduplicating, or editing a
connection preserves the ID. An unsaved connection produces an unbound query
and asks you to persist the connection before binding it.

Legacy `-- grip:url=` files remain readable when the URL is templated or has
no credentials. A credential-bearing legacy URL is never auto-connected: its
metadata is removed from the editor and a warning is shown without the secret.
The next explicit save converts a resolvable legacy binding to an ID.

                                                          *grip-secrets*
Secrets: ${VAR} in a connection URL ~

Any `${NAME}` in a url is resolved when you connect, so the password never
has to be stored in connections.json: >

  {
    "name": "dev",
    "url": "postgresql://api:${DEV_DB_PASSWORD}@dev.internal:5432/app",
    "env_file": "~/work/api/.env"
  }
<
Values come from `env_file` first and fall back to the process environment,
so `${PGPASSWORD}` works with no env_file at all.

A placeholder that cannot be resolved is an error, and so is one that
resolves to an EMPTY value: a bare `KEY=` is the usual shape of a committed
.env template, and substituting it would hand psql a url with no password,
which falls through to ~/.pgpass and may connect with a different credential
instead of failing. Either way the entry shows `?` in the picker and names
the variable when you try to connect.

If a literal password contains `${WORD}`, write `$${WORD}`: a doubled dollar
produces the literal text and resolves nothing. The escape is only special
immediately before `{NAME}`, so `pa$$word` is left alone.

The .env file supports `KEY=value` and `export KEY=value` lines. Whitespace
outside values and one surrounding quote pair are stripped. Whole-line `#`
comments and blank lines are ignored. An inline comment starts with whitespace
followed by `#` outside the quotes, so `KEY="value" # comment` and
`KEY=value # comment` both produce `value`. A quoted hash or an unspaced hash
stays literal: `KEY="value # suffix"` and `KEY=value#suffix` retain their hashes.

Values remain literal: backslash escapes and nested ${VAR} text are not decoded
or expanded, and multiline values and shell expressions are not supported.
Backslashes only help identify escaped quotes when finding the closing quote.
An unmatched quote or extra noncomment text after a closing quote is preserved
verbatim rather than silently truncating a credential. Inline comments require
separating whitespace, including after a closing quote.

It is read at connect time and memoized on the file's mtime, so a
rotated password is picked up on the next query. A git-crypt-locked file is
reported as such by name rather than as a parse error, and because failed
reads are never cached, `git-crypt unlock` takes effect on the very next
connect with no restart.

Grip stores and exposes the *template*: `vim.g.db` holds the url with the
placeholder still in it, and expansion happens at a single point on the way
to the database client. No code path that writes to disk ever sees the
expanded url. Passwords also reach psql, mysql, and sqlcmd through the process
environment rather than argv, so they are not visible in another user's `ps`.
Processes running as your user may still read those environment variables.

Grip sends original SQL and AI request content through stdin. Statements,
prompts, schema context, existing SQL, and JSON request bodies are absent from
argv. AI URLs and headers also travel through `curl --config -`, and API-key
lookup commands run through shell stdin. DuckDB attachment declarations use
the same stdin boundary. Credentialed PostgreSQL and MySQL attachments use
invocation-scoped temporary DuckDB secrets and attach by secret name. Grip
never creates persistent DuckDB secrets.

SQLite's lossless read path also uses a generated SQL script containing selected
column identifiers. It creates the script as 0600 inside a fresh 0700 temporary
directory and removes it after the client exits, including cancellation cleanup.
Identifiers can be sensitive. The original query and mutation values remain on
stdin, and the temporary path carries no connection credentials.

Limit: a templated url is grip-only. vim-dadbod's `:DB` and any statusline
reading `g:db` see the literal `${NAME}`. Keep such connections un-templated
if you depend on either.

                                                          *grip-readonly*
Read-only mode ~

With `"mode": "ro"` grip connects using the client's own read-only switch:

  postgresql   PGOPTIONS=-c default_transaction_read_only=on
  mysql        SET SESSION TRANSACTION READ ONLY through stdin
  sqlite       sqlite3 -readonly
  duckdb       duckdb -readonly
  sqlserver    already read-only; `mode` does not apply

Grid editing is disabled, and the DDL entry points (|:GripCreate|,
|:GripDrop|, |:GripRename|, |:GripFill|, the sidebar's create/drop, and the
column operations) decline up front instead of prompting and then failing at
the server. The winbar shows `RO` while connected read-only.

Press `r` in the connection picker to connect in the opposite mode for this
session only. The connections file is not modified.

This is a guard against accidents, NOT a security boundary. Each mechanism
above is reversible from the query pad -- on postgres, `begin; set
transaction read write; ...` is enough. If a connection must not be able to
write, give it a database role that cannot. That is the boundary; `mode` is
the seatbelt.

Three further limits:

- An `options=` already present in a postgres url wins over PGOPTIONS, so
  such a connection reports `RO` while its session is not read-only.
  Connecting it read-only warns once: it is the one case where the `RO`
  badge claims more than the server was actually told.
- `-readonly` is applied only to a database file that already exists.
  `duckdb::memory:` and a not-yet-created sqlite file connect normally: the
  flag aborts the former outright and turns "create it" into an error for
  the latter.
- A connection pooler refuses the option outright. Pgbouncer-compatible
  poolers reject unknown startup parameters, so PGOPTIONS does not degrade
  the session, it fails the connection: >

    FATAL: unsupported startup parameter in options:
    default_transaction_read_only
<
  Unlike the two above, this is not an overstated `RO` badge -- there is no
  session at all. Point a `mode: "ro"` entry at the direct port rather than
  the pooled one.

                                                          *grip-accent*
Connection colour ~

`"color"` takes a palette name -- green, orange, red, blue, violet,
yellow -- or a `#rrggbb` value, and tints the window borders, the grid
rules and the schema sidebar title, so a red production connection does not
look like a green local one. An unknown value is ignored, not raised.

The palette reuses colours already in grip's theme, and every accent also
carries a `ctermfg` (a `#rrggbb` value is approximated onto the nearest
xterm palette entry), so none of this needs a truecolor terminal.

Three highlight groups carry it:

  GripConnAccent       the connection's colour
  GripConnAccentBold   the same, bold; used for the sidebar title
  GripBorder           window borders and grid rules; DERIVED from the
                       accent, which is what makes an entry without a
                       `color` restore the default #cba6f7 / ctermfg=147
                       instead of leaving the last connection's tint behind

All three are redefined on every connection switch and re-applied whenever
highlights are rebuilt, so they survive a `:colorscheme` change. To customize
them persistently, use the `highlights` setup option (|grip-highlights|); those
overrides take precedence over the connection's accent.

16. ADAPTERS                                              *grip-adapters*

Grip supports five database adapters. The adapter is selected automatically
based on the connection URL scheme.

  postgresql:// .... PostgreSQL via psql CLI
  sqlite: .......... SQLite via sqlite3 CLI
  mysql:// ......... MySQL via mysql CLI
  mariadb:// ....... MariaDB via the compatible mysql CLI
  duckdb: .......... DuckDB via duckdb CLI
  sqlserver:// ..... SQL Server via sqlcmd CLI (read-only grids)
  mssql:// ......... SQL Server via sqlcmd CLI (alias)

Each adapter implements: query, execute, get_primary_keys, get_column_info,
get_foreign_keys, get_indexes, get_table_stats, list_tables, and explain.

MySQL/MariaDB translate `INSERT ... DEFAULT VALUES` into the native
`INSERT ... () VALUES ()` form. Translation recognizes mixed-case keywords
and ordinary comments while preserving quoted data, identifiers, and the
surrounding SQL. Inputs with executable comments, optimizer hints containing
client commands, SQL-mode or delimiter changes, or ambiguous/unfinished
quoting or comments are sent unchanged.
Use native `() VALUES ()` syntax for those inputs.

File-as-table: `:Grip /path/to/data.parquet` routes through DuckDB to
query supported files directly. No database connection is needed.

Supported extensions: .parquet .csv .tsv .json .ndjson .jsonl .xlsx .orc .arrow .ipc

Remote file querying: `:Grip https://example.com/data.csv` opens remote
files via DuckDB's httpfs extension. The extension is loaded automatically.
Remote/file queries use the configured 10-second CLI timeout, except DuckDB
work that may download httpfs/scanner extensions or read a remote URL gets a
60-second minimum. All remote queries open in read-only mode.

SQL Server validates the server certificate by default. Both sqlserver://
and mssql:// accept these URL query parameters:

  encrypt=optional|mandatory|strict
  trust_server_certificate=true
  server_certificate=<url-encoded-path>

server_certificate cannot be combined with trust_server_certificate=true
and requires mandatory or strict encryption.

Each SQL Server submission starts a new sqlcmd session. Create and use #temp
or ##temp tables in the same submitted block or visual selection. GO-separated
batches in one submission share that session, but temporary tables do not
persist into the next submission.

DuckDB federation: attach external databases via :GripAttach. Supports
PostgreSQL (postgres_scanner), MySQL/MariaDB (mysql_scanner), SQLite
(sqlite_scanner), and MotherDuck. See |grip-federation| for details.

20. TABLE PROFILING                                          *grip-profiling*

Profile table columns with `:GripProfile` or `gR` from a grid buffer.

Shows per-column statistics:
  - Unicode sparkline distributions (block characters)
  - Completeness percentage (non-NULL ratio)
  - Cardinality (distinct value count)
  - Min/max values for numeric and date columns
  - Top values with frequency counts

Adapts layout to terminal width. Narrow terminals get a stacked layout;
wide terminals get a tabular layout.

Profiling keymaps:
  q / <Esc>       Close profile float

21. QUERY DOCTOR                                        *grip-explain-full*

The Query Doctor translates raw EXPLAIN plans into plain-English health
checks. Run with `:GripExplain` or `gQ` from a grid buffer.

Output includes:
  - Severity labels: OK (green), WARN (yellow), SLOW (red)
  - Proportional cost bars showing relative expense of each operation
  - Actionable tips (e.g. "add an index on the filtered column")
  - Summary with estimated total cost and row count

Severity rules adapt to context:
  - Sequential scans on small tables (<1000 rows) downgrade to OK
  - Nested loops with few rows downgrade to OK
  - Filters with low cost (<500) downgrade to OK

Works across all five adapters:
  - PostgreSQL: full cost and actual timing from EXPLAIN ANALYZE
  - MySQL: cost and row estimates
  - DuckDB: estimated cardinality
  - SQLite: EXPLAIN QUERY PLAN operations
  - SQL Server: SHOWPLAN_TEXT operator tree, no cost estimates

22. AI SQL GENERATION                                             *grip-ai*

Generate SQL from natural language with :GripAsk, `A` from a grid, or `gA`
from the query pad. In a grid, `gA` is intentionally different: it stages
one AI-generated row, the same as :GripFill 1.

  :GripAsk show me the top 5 users by order count

Schema context is auto-assembled from database metadata (table names,
column names, types, primary keys, foreign keys). The generated SQL
appears in the query pad for review before execution.

Supported providers:
  - Anthropic (Claude) via ANTHROPIC_API_KEY
  - OpenAI (GPT) via OPENAI_API_KEY
  - Google Gemini via GEMINI_API_KEY
  - Ollama (local) as automatic fallback

Auto-detection priority: Anthropic > OpenAI > Gemini > Ollama.
Override with setup({ai={provider="openai"}}).

API key resolution: env var name, "env:CUSTOM_VAR", "cmd:op read ...",
or a direct string. See |grip-config| for the full ai config block.

To disable AI entirely (skips schema pre-warm on connection open): >lua
  require("dadbod-grip").setup({ ai = false })
<
Pressing A or gA while AI is disabled shows an informational message.

23. CROSS-DB FEDERATION                                    *grip-federation*

DuckDB can attach external databases and query across them in a single
session. Grip exposes this through :GripAttach and :GripDetach commands.

Attach a PostgreSQL database: >
  :GripAttach postgres:dbname=sales host=localhost user=me  pg
<
Attach a MySQL or MariaDB database: >
  :GripAttach mariadb://user:${DB_PASSWORD}@localhost/sales  maria
<
Attach a local SQLite file: >
  :GripAttach sqlite:legacy.db  legacy
<
Query across both plus the local DuckDB: >
  :Grip SELECT p.name, l.total
    FROM pg.customers p
    JOIN legacy.orders l ON p.id = l.customer_id
    WHERE l.total > 1000
<
The schema sidebar groups tables by database when attachments are active:

  main (12 tables)
  pg (8 tables)
  legacy (3 tables)

MotherDuck (cloud DuckDB) works as both a primary connection and an
attachment: >
  :GripAttach md:shared_analytics  cloud
<
Extensions are managed automatically. Attaching a postgres: DSN installs
and loads postgres_scanner. Attaching mysql: or mariadb: loads mysql_scanner.
Attaching sqlite: loads sqlite_scanner. Attaching md: loads motherduck.

Attachments persist in .grip/connections.json under the parent DuckDB
connection. They restore automatically when you reconnect.

Sidebar keymaps for federation (DuckDB connections only):
  ga              Attach external database (prompts for DSN and alias)
  gd              Detach attached database (prompts for alias)

24. S3 AND REMOTE FILES                                       *grip-s3-files*

DuckDB can query remote files directly via the httpfs extension.

HTTPS files (no credentials needed): >
  :GripOpen https://example.com/data.parquet
<

S3 files (with credentials in environment): >
  :GripOpen s3://my-bucket/data/report.parquet
<

S3 prefix (browse bucket contents): >
  :GripOpen s3://my-bucket/data/
<
  Opens the query pad pre-filled with a glob() query.

Save a remote file as a named connection: >
  gc → + New connection → paste URL → give it a name
<

Cross-federation with remote files: >
  SELECT l.user_id, r.event_date
  FROM local.users l
  JOIN read_parquet('s3://my-bucket/events.parquet') r ON l.user_id = r.user_id
<

For S3 access, set AWS_ACCESS_KEY_ID and AWS_SECRET_ACCESS_KEY in your
environment. Public buckets work without credentials.
DuckDB's httpfs extension installs automatically on first use.

25. HEALTH CHECK                                              *grip-health*

Run the built-in health checker to verify your installation: >
  :checkhealth dadbod-grip
<

Checks performed:

  Neovim version     Confirms Neovim >= 0.10 is installed.

  Database CLIs      Checks psql, sqlite3, mysql, duckdb, and sqlcmd in PATH.
                     Reports WARN for any missing (only the adapters you use
                     are required).

  AI providers       Checks ANTHROPIC_API_KEY, OPENAI_API_KEY, GEMINI_API_KEY,
                     or an installed ollama executable. Ollama alone satisfies
                     the check because it needs no API key.

Example output: >
  dadbod-grip
    OK  Neovim >= 0.10
    OK  psql found
    OK  sqlite3 found
    WARN  mysql not found (required for that adapter)
    OK  duckdb found
    WARN  sqlcmd not found (required for that adapter)
    OK  Anthropic API key set (ANTHROPIC_API_KEY)
<
